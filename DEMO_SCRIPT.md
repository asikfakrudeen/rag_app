# AI Summit Demo Script — Four-Part Demo
## Legal Contract Review Assistant · Track F · Week 12

> **Time budget:** ~5 minutes total. Keep each part tight.
> This is your cheat sheet — read it, then put it away and demo live.

---

## Before You Go On Stage

```powershell
# Terminal 1 — start the whole app
python main.py

# Terminal 2 — keep open for the support-drill step
```

- Have a sample contract PDF ready (e.g. a vendor agreement or MSA)
- Open `http://localhost:8501` in your browser in advance
- Open `traces.jsonl` in VS Code so you can show a raw trace if asked

---

## Part 1 — The Real Run (≈ 60 seconds)

**What you show:** the app answering a real question end-to-end.

1. Go to the Streamlit UI (`http://localhost:8501`)
2. Upload the sample PDF → click **Build Index** → wait for "Indexed N chunks"
3. In the question box type:

   > *"What is the termination notice period in this contract?"*

4. Click **Ask** — point out:
   - The answer text
   - The **Fetched Evidence** panel (source filename + page numbers)
   - The **Trace ID** returned (proves every request is logged)

**What to say:** *"This is the full pipeline — document loaded, chunks retrieved with hybrid BM25 + vector search, answer generated by Gemini 2.0 Flash, and the complete trace written to disk with a unique ID."*

---

## Part 2 — The Real Failure (≈ 90 seconds)

**What you show:** a bug you found yourself, before anyone else did.

1. Switch to Terminal 2 and run:
   ```powershell
   .\.venv\Scripts\python.exe scripts/support_drill.py
   ```
2. The script will surface a trace where the assistant hallucinated **60 days** instead of the correct **30 days**.
3. Show the trace output — the exact chunks that were fed to the LLM, exposing *why* it went wrong (BM25 over-weighted "60 days" from an unrelated amendment clause).
4. Then show the regression test that now protects against it:
   ```powershell
   .\.venv\Scripts\python.exe scripts/test_termination_regression.py
   ```

**What to say:** *"I didn't hide this failure — I found it through traces, diagnosed the root cause (BM25 keyword collision), and added a permanent regression test. The trace log is how you do post-incident analysis at scale."*

## Part 3 — A Number That Improved (≈ 60 seconds)

**What you show:** a measurable improvement backed by data.

Run (or show pre-run output of):
```powershell
.\.venv\Scripts\python.exe scripts/race_multi_vs_single.py
```

Point to the quality score column in the race report:

| System | Quality (1–5) | Latency | Cost/query |
|--------|--------------|---------|------------|
| Single ReAct Agent (W9) | 3.2 | ~4 s | ~$0.0003 |
| Multi-Agent Squad (W10) | **4.1** | ~11 s | ~$0.0009 |

**What to say:** *"The multi-agent squad scores 28% higher on answer quality for complex reasoning tasks. The trade-off is 2.7× higher cost and 2.5× higher latency — so it's used selectively. That's an engineering decision, not a guess."*

> **If asked about hybrid search improvement:**
> Eval suite shows HitRate@5 went from **0.50** (vector only) to **1.00** (hybrid + rerank).

## Part 4 — What's Next (≈ 30 seconds)

Three honest next steps if this were going to production:

1. **Semantic caching** — cache LLM answers for semantically identical questions, cutting average cost by ~60% under repeated load (Week 11 concept, not yet implemented)
2. **Routing guard** — auto-detect simple vs complex questions and route simple ones to the cheap single agent, saving 3× tokens
3. **Fine-tuning pipeline** — use the failure traces already logged in `traces.jsonl` as a labelled dataset to fine-tune an answer quality model; this is the data flywheel (Week 11)
